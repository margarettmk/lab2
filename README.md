# Лабораторная работа № 2 — Анализ уязвимостей веб-приложения

## Дисклеймер

**Проект создан исключительно в образовательных целях в рамках лабораторной работы по информационной безопасности.**

Веб-приложение намеренно содержит уязвимости для изучения механизмов их возникновения, демонстрации последствий и способов устранения.

**Условия безопасного использования:**
- Все проверки выполняются исключительно в локальной среде на собственном компьютере (`127.0.0.1`).
- Проект использует вымышленные учётные записи и тестовые данные.
- Программы демонстрации уязвимостей предназначены только для взаимодействия с приложением из данного репозитория.
- Запрещается применять представленные методы для получения несанкционированного доступа к сторонним информационным системам.
- Уязвимая версия приложения не предназначена для размещения в публичной сети или эксплуатации в производственной среде.

Автор проекта не одобряет неправомерное использование представленных материалов.

## 1. Описание проекта

Данный проект представляет собой учебное веб-приложение на языке Python, разработанное для изучения распространённых уязвимостей веб-приложений.

В рамках лабораторной работы реализованы две уязвимости, описанные в классификации **OWASP Top 10 (2021)**:

1. **SQL Injection (SQL-инъекция)** — внедрение SQL-кода, позволяющее обойти проверку пароля.
2. **IDOR (Insecure Direct Object Reference)** — получение доступа к чужим данным вследствие недостаточной проверки прав доступа.

Для каждой уязвимости предусмотрены:
- Исходная версия приложения с намеренно допущенной ошибкой безопасности.
- Программа автоматической демонстрации уязвимости.
- Исправленная версия приложения.
- Проверка эффективности исправления.

Проект позволяет сравнить поведение приложения до и после устранения уязвимостей.

## 2. Используемые технологии

- Язык программирования: Python 3.9+

- База данных: SQLite

Все основные компоненты реализованы с использованием стандартной библиотеки Python. Установка сторонних библиотек не требуется.

## 4. Реализованные уязвимости

### 4.1. SQL Injection — SQL-инъекция

**Категория OWASP Top 10 (2021): A03 — Injection.**

Уязвимость возникает из-за формирования SQL-запроса путём непосредственного включения пользовательского ввода.

При таком подходе специальные символы могут изменить структуру SQL-запроса.

В учебном приложении это позволяет выполнить вход в учётную запись без знания правильного пароля.

**Демонстрация:**

Программа `exploit.py` отправляет специально сформированный запрос авторизации.

Результат на уязвимой версии:

```text
SQL injection bypasses password verification:
HTTP 200
```

Код HTTP 200 и возвращённые данные пользователя подтверждают успешный обход проверки пароля.

**Исправление:**

Используются параметризованные SQL-запросы, в которых пользовательский ввод обрабатывается как данные, а не как часть SQL-команды.

После исправления попытка обхода авторизации отклоняется:

```text
SQL injection: 401
```

### 4.2. IDOR — нарушение контроля доступа

**Категория OWASP Top 10 (2021): A01 — Broken Access Control.**

Уязвимость возникает, когда приложение предоставляет доступ к объекту по его идентификатору без достаточной проверки прав пользователя.

В учебном приложении хранятся записи, принадлежащие разным пользователям.

В исходной версии пользователь № 1 может получить запись пользователя № 2, указав её идентификатор в HTTP-запросе.

**Демонстрация:**

```text
IDOR: user 1 reads note belonging to user 2:
HTTP 200
```

Ответ сервера содержит чужую запись.

**Исправление:**

При обработке запроса выполняется проверка соответствия идентификатора владельца записи и идентификатора запрашивающего пользователя.

После исправления содержимое чужой записи не возвращается:

```text
Cross-user note access:
{'error': 'Note not found'}
```

При этом пользователь сохраняет возможность получать собственные записи.

**Ограничение реализации:** в данном учебном примере идентификатор запрашивающего пользователя передаётся в параметрах запроса. Полноценная система должна определять пользователя через проверенный сервером механизм аутентификации и авторизации. Поэтому исправление демонстрирует принцип проверки владельца, но не является завершённой системой безопасности для производственного использования.

## 5. Запуск проекта

### 5.1. Требования

Для запуска необходимо:

- Python версии 3.9 или новее.
- Терминал Windows PowerShell или другая командная оболочка.
- Локальная копия проекта.

### 5.2. Запуск уязвимого приложения

Откройте терминал в корневой папке проекта и выполните:

```bash
py app.py
```

После запуска появится сообщение:

```text
LOCAL TRAINING ONLY: http://127.0.0.1:8000
```

Приложение будет доступно по локальному адресу `http://127.0.0.1:8000`.

Оставьте сервер работающим.

### 5.3. Демонстрация уязвимостей

Откройте второй терминал в папке проекта.

Выполните:

```bash
py exploit.py
```

Программа последовательно выполнит:

1. Проверку входа с неправильным паролем.
2. Демонстрацию SQL-инъекции.
3. Демонстрацию нарушения контроля доступа.

При успешном воспроизведении уязвимостей появится сообщение:

```text
Both vulnerabilities reproduced.
```

### 5.4. Запуск исправленной версии

Остановите исходный сервер сочетанием `Ctrl + C`.

Запустите исправленное приложение:

```bash
py app_fixed.py
```

В другом терминале выполните проверку:

```bash
py verify_fixed.py
```

При успешном выполнении появится сообщение:

```text
Both attack scenarios blocked. Authorized note retrieval still works.
```

Это означает, что проверяемые сценарии атак заблокированы, а доступ пользователя к собственной записи сохранён.

**Примечание:** в данной реализации попытка обращения к чужой записи возвращает сообщение `Note not found` с кодом HTTP 200. Более корректной обработкой для полноценного веб-приложения является возврат кода HTTP 403 или 404.

## 6. Сравнение результатов

| Проверка | Уязвимая версия | Исправленная версия |
|---|---|---|
| Вход с неправильным паролем | Отклонён | Отклонён |
| SQL-инъекция | Успешный обход авторизации | HTTP 401 |
| Получение чужой записи | Данные раскрываются | Данные скрыты |
| Получение собственной записи | Доступ разрешён | Доступ разрешён |

Результаты демонстрируют эффективность внесённых изменений для предусмотренных учебных сценариев.

## 7. Файл исправлений

Для документирования изменений используется файл `fix.patch` в формате `diff`.

Он позволяет определить:

- Какие строки исходного кода были изменены.
- Какие конструкции приводили к возникновению уязвимостей.
- Какие изменения были внесены для устранения ошибок безопасности.

Исправленная версия приложения также представлена отдельным файлом `app_fixed.py`.
